# IOHC 1W multi-bridge protocol

This document defines the firmware side of the Home Assistant multi-bridge
contract. It extends the existing single-bridge manager without changing the
on-air IOHC protocol, pairing a second controller, or allowing two bridges to
own the same rolling-code stream.

The initial implementation is deliberately limited to hardware-verified IOHC
1W shutters. It does not add automatic failover or IOHC 2W support.

## Roles and invariants

Home Assistant assigns two transmission roles per shutter:

- **primary bridge** (required): owns the controller node ID, AES key and
  rolling-code NVS stream;
- **secondary transmitter** (optional): can retransmit a single, exact frame
  produced by the primary, but owns no copy of that controller identity.

Every online bridge is also a receiver. Receiver diversity is independent of
the transmission assignments.

The following invariants are mandatory:

1. Exactly one live bridge owns and advances a controller identity.
2. A secondary never generates or authenticates a controller command and
   never advances a rolling code.
3. An observation update changes only the local position/tilt estimator. It
   cannot transmit RF, invoke PROG, or consume a rolling code.
4. A controller transfer disables the source durably before the identity is
   written to or activated on the destination. Source cleanup may follow
   destination activation because the archived source cannot transmit.
5. Existing local cover control continues to work when Home Assistant or every
   other bridge is unavailable.

## Firmware capabilities and services

The manager advertises the multi-bridge capabilities in its versioned status
JSON. Older fields and the existing status version remain backward compatible.

The additive native API services are:

```text
somfy_redundant_control(slot, command, relay_token)
somfy_relay(action, payload)
somfy_observe(slot, command, steps)
somfy_transfer(action, slot, transfer_token, encrypted_backup)
```

Slot numbers in these low-level services are zero based, like the existing
manager API. Home Assistant presents one-based slot numbers to users and must
perform the conversion at its boundary.

Relay tokens are generated by the armed secondary, and transfer tokens are
generated by the source during prepare. Home Assistant carries those tokens
between bridges for correlation; it does not invent them. They are opaque to
users and contain no controller keys or other secret material.

## Redundant transmission

Redundant transmission is allowed only for the idempotent, ordinary commands
`open`, `close`, and `stop`. It follows a guarded, primary-first exchange:

1. Home Assistant calls `somfy_relay(action=arm, payload="")` on the selected
   secondary.
2. The secondary generates and records a short-lived, single-use token and publishes
   `relay_armed` with `relay_token`.
3. Home Assistant calls `somfy_redundant_control` on the primary with the same
   token.
4. The primary advances its rolling code, constructs and transmits the command
   normally, and only after the local transmission finishes publishes
   `relay_offer`. The status contains `relay_token`, `command`, and an opaque
   `relay_envelope` containing the canonical logical frame and repeat count.
5. Home Assistant passes that envelope unchanged to
   `somfy_relay(action=send, payload=<relay envelope>)` on the armed secondary.
6. The secondary validates the token and envelope, consumes the arm before RF,
   retransmits the exact authenticated frame, and publishes `relay_sent`.
7. Home Assistant may call `somfy_relay(action=cancel, payload=<relay token>)`
   when a primary command fails or a transaction times out. Firmware publishes
   `relay_cancelled`.

The arm is consumed before transmission so an API retry cannot create another
secondary burst. Arms expire and are lost harmlessly on reboot. Relay tokens
are never accepted twice.

### Relay frame allow-list

The secondary treats the envelope as untrusted input. The logical frame must
pass every check below before the CC1101 is used:

- exactly 25 bytes;
- `ctrl0 == 0xF6` (declared IOHC length 22 plus the two-byte CRC);
- canonical `ctrl1 == 0x00`; the radio hub adds the first-copy wake bit itself;
- destination bytes `00 00 3F` (IOHC broadcast);
- a non-zero 24-bit source node;
- command byte `0x00` (`CMD_EXECUTE`);
- ordinary six-byte data `01 43 <main parameter> 00 00`;
- main parameter is exactly `0x0000` (OPEN), `0xC800` (CLOSE), or `0xD200`
  (STOP);
- the complete logical frame has a valid CRC-16/KERMIT residue;
- repeat count is within the firmware's configured safe bound.

The secondary cannot validate the six-byte MAC because it intentionally does
not possess the controller key. Structural validation, the encrypted ESPHome
API, the short-lived arm, and the single-use token form the safety boundary.

MY, intermediate positions, Venetian tilt, button-event frames, PROG, key
transfer, and every unknown command are rejected. In particular, the ordinary
`D200` pre-stop that begins a MY gesture must not emit a relay offer. Two fresh
MY gestures are not idempotent: the second can stop the movement started by the
first.

Calling the existing hub `transmit_packet()` with the primary's canonical frame
recreates the same first-copy wake-bit variant and canonical repeat copies. The
secondary therefore repeats the primary's already-authenticated rolling
sequence; it does not create a second command.

## Composite command completion

Composite local operations expose an explicit terminal status. A complete
native MY publishes `command_complete` with detail `my` after its authenticated
release frame. A Venetian tilt sequence publishes `command_complete` with
detail `tilt` after its final direction event and final estimator update. The
tilt callback is deferred by one loop when needed so `command_sent` remains
observable before the terminal status.

The handoff between queued MY transactions is 150 ms. This is still much
faster than the former automation workaround, while keeping the preceding
`command_complete` state visible across ESPHome native API's default 100 ms
batching interval before the next shutter can publish another status.

## Global receive observations

The manager decodes physical remote traffic once per bridge, independently of
the bridge's locally owned slots. This lets a newly installed, empty bridge
participate in receiver diversity.

Manager-owned covers do not also run their former per-cover RX path. The
manager applies a decoded gesture once to matching local covers and emits one
`remote_observation` status with:

```text
observation_v = 1
remote        = 24-bit physical remote identity
command       = open | close | stop_my | tilt_clockwise | tilt_counterclockwise
sequence      = received rolling sequence, when available
has_sequence  = whether sequence is usable
complete      = whether this is terminal rather than prefix-only evidence
steps         = normalized Venetian step magnitude (at least one)
rssi          = received signal strength
slot_mask     = unsigned 32-bit mask of locally matched zero-based slots
```

A zero `slot_mask` is valid and important: that receiver may be the only bridge
which heard a remote belonging to a shutter owned elsewhere. Bit `n` targets
firmware slot `n`; the full unsigned 32-bit value therefore represents every
allowed `max_shutters` configuration while keeping the ESPHome text state below
its 255-byte transport limit.

The manager collapses repeated copies from one RF burst locally. Home Assistant
then deduplicates observations from all bridges using physical remote,
sequence, normalized command and a bounded arrival window. It retains the
receiver set and strongest RSSI for diagnostics. New presses with a new rolling
sequence remain distinct, including after a bridge reboot.

For STOP/MY and Venetian wheel gestures, the direction/button-event frame is
the authoritative terminal action. A terminal STOP/MY or tilt observation uses
that terminal frame's sequence and sets `complete=true`. The correlated
`D200` prefix supplies Venetian magnitude; a direction event received without
its prefix is still complete but reports one step rather than invented
magnitude.

A `D200` prefix which reaches its local correlation timeout without a terminal
frame is emitted as `stop_my` with the prefix sequence and `complete=false`.
That evidence may be a genuine lone STOP, or it may come from a receiver which
missed the terminal half of a gesture heard elsewhere. Firmware therefore
applies its local meaning after the bounded wait, while Home Assistant briefly
holds cross-bridge incomplete evidence for fusion.

If the same physical remote produces a complete `stop_my`,
`tilt_clockwise`, or `tilt_counterclockwise` observation at the next 16-bit
rolling sequence within the gesture window, Home Assistant suppresses the
held incomplete `stop_my` and applies only the terminal action. The comparison
is sequence-aware, including the unsigned 16-bit boundary. When one capture
lacks a usable sequence, the same-remote bounded time window is the fallback.
If no matching terminal arrives, the incomplete observation is released once
and treated as the genuine lone STOP/MY action.

Frames sent by known virtual controller node IDs are not physical-remote
observations. Home Assistant maintains the global controller-node directory and
filters them even when the receiving bridge does not own that node locally.

## Estimator-only forwarding

After deduplication, Home Assistant calls `somfy_observe` for each affected
shutter whose owner did not already apply the observation locally.

Allowed commands are:

- `open`
- `close`
- `stop_my`
- `tilt_clockwise`
- `tilt_counterclockwise`

`steps` is ignored for lift commands and is clamped to at least one for tilt.
The service accepts active slots only and calls dedicated estimator methods; it
does not enter the cover control path. Consequently it cannot build a frame,
touch the radio hub, call `nextCode()`, or trigger a relay offer.

Home Assistant must consider every bridge that reported the winning
observation. If the owning bridge is among those reporters, it already applied
the command locally and must not receive the forwarded update. This avoids a
double Venetian step when a different receiver happened to have the strongest
RSSI.

Successful application publishes `observation_applied`. Invalid slots or
commands fail closed.

## Controller ownership transfer

Moving a shutter's primary assignment reuses its existing paired identity. It
does not send PROG and does not consume another receiver slot in the motor.

`somfy_transfer` supports these actions:

- `prepare`
- `import`
- `activate`
- `commit`
- `finalize`
- `abort`
- `rollback`
- `query`

The normal transaction is:

1. **Prepare source.** Reject a busy controller, snapshot the authoritative
   next rolling code, create a persistent transfer journal, mark the source
   record `ARCHIVED`, commit it, and disable its runtime transmitter. Only then
   publish the encrypted archived record through the existing backup sensor,
   followed by `transfer_prepared` with `transfer_token`.
2. **Import destination.** Decrypt and validate the archived record, require an
   empty destination and matching token, assign a destination-local NVS key,
   and explicitly seed that key to the transferred next rolling code. Persist
   the record as `ARCHIVED` and publish `transfer_imported`. It cannot transmit.
3. **Activate destination.** After Home Assistant has verified that the source
   is durably archived and the destination import is complete, change the
   imported record and its destination journal from `ARCHIVED` to `ACTIVE`
   durably and enable its cover. Retain that journal and publish
   `transfer_activated`. The source remains archived and cannot transmit.
4. **Commit source.** After destination activation is confirmed, remove the
   disabled source record and journal, then publish `transfer_committed`.
5. **Finalize destination.** After source commit is confirmed, erase the
   destination's now-active transfer journal and publish `transfer_finalized`.
   The active controller record and rolling-code storage remain untouched.

The integration persists its orchestration phase so a Home Assistant restart
can query both bridges and continue rather than guessing. `query` is accepted
with `slot=-1` to inspect the bridge's single global transfer journal, even
though every mutating action requires a valid slot. Its `transfer_state` result
contains `slot`, `transfer_token`, `role` (`source`, `destination`, or `none`),
and `phase`. A destination journal remains queryable with role `destination`
and phase `active` after activation, until finalization proves source cleanup.
With no journal, a global query reports role/phase `none`; a specific-slot
query reports that slot's persisted phase such as `empty`, `archived`, or
`active`.

`prepare` and `import` are convergent retry operations. Repeating `prepare` for
the source slot with its existing source journal restores and persists the
same archived record, republishes its backup, and re-emits the original token;
it never generates another identity or token. Repeating `import` with the same
destination slot and token restores the exact journaled phase and reseeds the
same next rolling code. An archived journal re-emits `transfer_imported`; an
already-active journal stays active and re-emits `transfer_activated`. A retry
must never demote an active destination. A mismatched role, slot or token
remains an error.

The explicit NVS seed is essential. Manager rolling-code keys are local to a
slot, and an empty slot may retain a value from an older identity. Merely
setting `initial_rolling_code` is insufficient because NVS storage correctly
prefers an existing key. The seed operation therefore opens the namespace/key
stored in the destination's managed record directly; it must not depend on a
cover storage object which may still reference an empty-slot default or may not
exist yet during early boot. Activation is forbidden unless the exact
transferred next code was written successfully.

Disabling a runtime controller is a hard quiescence boundary. It cancels MY
and Venetian timers, clears pending receive correlation, freezes any active
time-based position animation without firing its STOP trigger, and prevents a
previously scheduled intermediate-position STOP from transmitting after the
archive. Reboot recovery applies the same disabled state before continuing the
transaction.

Before destination activation, `abort` removes the disabled destination import
and publishes `transfer_aborted`; once that absence is confirmed, `rollback`
reactivates the archived source and publishes `transfer_rolled_back`. Rollback
must never run while a destination copy can still be active. After destination
activation, recovery proceeds by committing the archived source and finalizing
the destination rather than reactivating the source.

Power loss at every phase leaves zero or one active owner:

- after prepare: source archived, destination absent;
- after import: both copies archived;
- after activate: source archived, destination active with its journal;
- after commit: source absent, destination active with its journal;
- after finalize: source absent, destination active without a journal.

The transfer journal is validated and recovered at boot. A malformed or
ambiguous journal fails closed. Source recovery always converges to archived
and disabled. Destination recovery honors the journal record: an archived
import remains archived and disabled, while a destination already durably
activated remains active. After ordinary initial backups, a recovered source
re-emits `transfer_prepared`; a recovered destination re-emits
`transfer_imported` or `transfer_activated` according to its durable phase.
Every recovery event includes the slot and original token. This allows Home
Assistant to resume after a bridge reboot without relying on a missed
pre-reboot event.

## Status actions

The multi-bridge flow uses these additive status actions:

```text
relay_armed
relay_offer
relay_sent
relay_cancelled
remote_observation
observation_applied
command_complete
transfer_prepared
transfer_imported
transfer_activated
transfer_committed
transfer_finalized
transfer_aborted
transfer_rolled_back
transfer_state
```

Relay statuses include `relay_token`, `command`, and `relay_envelope` where
relevant. Observation statuses include the fields listed above. Transfer
statuses include `transfer_token`. `transfer_state` also includes `role` and
`phase`. Secrets and decrypted controller records must never enter ordinary
logs or the general status entity.

## Validation before release

At minimum, test with two real ESP32 + CC1101 bridges:

- OPEN, CLOSE and STOP with primary reception blocked in turn, confirming the
  exact secondary copy works and one rolling code is consumed;
- rejection of MY, position, tilt, management and malformed relay frames;
- arm expiry, duplicate `send`, delayed envelopes and bridge reboot;
- one remote heard by one and both bridges, applied once;
- an empty bridge being the sole receiver;
- two distinct rapid presses and rolling-sequence rollover;
- Venetian prefix/event correlation and direction-only fallback;
- an incomplete D200 observation from one bridge superseded by the adjacent
  complete STOP/MY or tilt terminal from another, plus lone-prefix release;
- transfer power loss after each durable phase;
- global and per-slot transfer query, reboot re-emission, and repeated
  prepare/import convergence;
- a previously used destination slot receiving the exact transferred rolling
  code rather than its stale NVS value;
- source rollback only after destination abort;
- ordinary single-bridge control while Home Assistant is unavailable.
